# RioMisc MVP-2.5 极致详细开发指南

## Batch Contest Orchestration + Manager Dispatch + Single Solver + Optional LLM Reflection

**目标版本：** MVP-2.5
**基线：** 当前 MVP-2
**核心目标：** 一轮出现 30～100 道 Misc/Crypto 题时，由 Manager Agent 根据全局状态选择优先派发哪些题；每题始终只有一个 Solver；Solver 可以配置是否启用独立 Reflector。
**明确延后：** Challenger、多 Solver Branch、Experience、Skill Learning、复杂 EV 学习、Sage/LLL 深度后端。

---

# 0. MVP-2.5 最终定义

MVP-2.5 不再是：

```text
Challenge
→ Scheduler 排个序
→ 有空位就启动
```

而应该变成：

```text
                    Competition API
                           │
                           ▼
                 30 ~ 100 Challenges
                           │
                           ▼
                 Prepare / Cheap Triage
                           │
                           ▼
                  Manager Snapshot
                           │
                           ▼
                     Manager Agent
                           │
                     Dispatch Plan
                           │
                           ▼
                     Policy Engine
                           │
                           ▼
                       Scheduler
                           │
           ┌───────────────┼───────────────┐
           ▼               ▼               ▼
      Challenge A     Challenge B     Challenge C
           │               │               │
         Solver           Solver          Solver
           │               │               │
       Reflector?      Reflector?      Reflector?
        optional        optional        optional
```

**最核心约束：**

```text
1 Challenge = 1 Solver Worker
```

任何时候都不能：

```text
Challenge A
├─ Solver 1
└─ Solver 2
```

Challenger / 多 Solver Branch 明确留给 MVP-3 或以后。

# 1. 当前代码基线

当前仓库中 Reflection 仍主要是 heuristic：根据 Wrong Flag、NO_SIGNAL、停滞、重复实验等状态生成诊断，不是真正独立调用模型的 Reflector。

但项目已经有：

```text
reflection.md
reflectionModelId
shouldReflect()
```

所以升级成真正 LLM Reflection 的基础已经存在。

同时目前 WorkerPool 明确以 `challengeId` 为唯一 Worker Key，所以天然符合 MVP-2.5 的“一题一 Solver”设计，不需要进行 Branch 重构。

# 6. 新增 Advisory Agent Runtime

Manager 和 Reflector 有一个共同特点：

> 都需要模型，但是都不是长期 Solver。

所以不要为两者各写一套模型调用逻辑。

增加：

```ts
interface AdvisoryAgentRuntime {
    runStructured<T>(input: {
        model: ModelRef;

        systemPrompt: string;
        userPrompt: string;

        schema: ZodSchema<T>;

        timeoutMs: number;

        task:
            | "MANAGER"
            | "REFLECTION";
    }): Promise<AdvisoryResult<T>>;
}
```

返回：

```ts
interface AdvisoryResult<T> {
    ok: boolean;

    value?: T;

    modelId: string;

    providerId: string;

    durationMs: number;

    inputTokens: number;
    outputTokens: number;

    error?: {
        code: string;
        message: string;
        retryable: boolean;
    };
}
```

---

# 7. Advisory Runtime 的行为原则

它：

```text
不使用 Solver Workspace
不启用 Tool
不启用 Bash
不运行 Python
不建立长期业务 Session
```

生命周期：

```text
build input
↓
call model
↓
parse structured result
↓
return
↓
销毁
```

Manager / Reflector 的真实状态始终来自数据库。

不要让：

```text
Manager Conversation
```

成为 source of truth。

---

# 8. Structured Output 失败策略

不是所有 Provider 都保证 Structured Output。

因此：

```text
模型支持 structuredOutput
→ 使用 Provider 原生 structured output

否则
→ Prompt 要求 JSON
→ Zod parse
```

第一次 parse 失败：

```text
允许一次 repair retry
```

Repair Prompt：

```text
Your previous response did not match the required JSON schema.

Return ONLY a corrected JSON object.
Do not add markdown or explanation.
```

第二次仍失败：

```text
ADVISORY_OUTPUT_INVALID
```

然后 fallback。

禁止无限 retry。

# Part I — LLM Reflection

# 9. Reflection 的正式定位

Reflector 是：

> **无工具、短生命周期、独立视角的 Solver Reviewer。**

它不是第二 Solver。

它不能：

```text
运行 Python
调用 inspect_file
写 solve.py
生成 Artifact
提交 Flag
```

它只做：

```text
审查已有证据
指出假设问题
指出遗漏
建议下一轮最有判别力的实验
```

---

# 10. Reflection 四模式

新增：

```ts
type ReflectionMode =
    | "OFF"
    | "HEURISTIC"
    | "LLM"
    | "HYBRID";
```

---

# 11. OFF

```text
完全不自动 Reflection
```

手工 Force Reflection：

建议也遵循 OFF。

也就是说：

```text
OFF = 真正关闭
```

如果用户强制要反思，可以先临时切模式或者提供单独：

```text
Run One Reflection
```

按钮绕过自动开关。

---

# 12. HEURISTIC

完全保留现在：

```text
shouldReflect()
+
buildReflection()
```

特点：

```text
便宜
稳定
无额外 LLM
```

---

# 13. LLM

Gate 触发后：

```text
ReflectionSnapshot
↓
Reflection Model
↓
ReflectionResult
↓
inject Solver
```

如果 Model 失败：

```text
记录 FAILED
```

不自动 heuristic fallback。

这就是纯 LLM 模式的语义。

---

# 14. HYBRID

推荐默认：

```text
Reflection Gate
↓
LLM Reflection
│
├─ success
│     ↓
│  inject
│
└─ failure
      ↓
 heuristic
      ↓
 inject
```

因此：

```text
HYBRID
```

同时具有：

```text
LLM 独立判断能力
+
Heuristic 可靠 fallback
```

---

# 15. Reflection Gate

当前 `shouldReflect()` 已有价值，应继续保留。

推荐触发条件：

```text
Wrong Flag >= 1

连续 NO_SIGNAL >= 3

120 秒没有 meaningful progress

重复 Tool Experiment

Solver 主动 request_reflection

人工 Force Reflection
```

---

# 16. Reflection Trigger 类型

正式定义：

```ts
type ReflectionTrigger =
    | "STALLED"
    | "NO_SIGNAL_STREAK"
    | "WRONG_FLAG"
    | "REPEATED_EXPERIMENT"
    | "SOLVER_REQUEST"
    | "MANUAL";
```

---

# 17. 不要只用 cooldown 防重复

现有 5 分钟 cooldown 可以继续保留，但还应该增加：

```text
Reflection Fingerprint
```

比如：

```ts
hash({
    latestProgressId,
    latestExperimentId,
    wrongSubmissionCount,
    hintCount,
    hypothesisUpdatedAt
})
```

如果：

```text
当前 fingerprint
==
上一次 reflection fingerprint
```

即使 cooldown 已过：

```text
不再次反思
```

因为没有新信息。

---

# 18. Reflection Cooldown

默认：

```text
5 min
```

配置：

```yaml
reflection:
  cooldownMs: 300000
```

以下情况可以 bypass cooldown：

```text
MANUAL
新 WRONG Flag
```

但 Fingerprint 仍可以防止 accidental duplicate。

# 22. Reflector Prompt

建议系统 Prompt：

```text
You are an independent reviewer for one authorized CTF solver.

You DO NOT solve the challenge directly.
You DO NOT have tools.
You DO NOT submit flags.

Your job is to audit the current solver state.

Look specifically for:

- assumptions that were never validated;
- evidence that contradicts the current direction;
- evidence the solver ignored;
- experiments that were repeated or had low information value;
- cheap discriminating tests that can eliminate competing hypotheses;
- overcommitment to one technique;
- signs that a Misc/Crypto handoff is appropriate.

Do not reproduce the solver's existing plan unless it remains clearly justified.

Return conclusions only, not hidden reasoning.
Return the required structured JSON.
```

# 24. Worker 不在线怎么办

Reflection 可能完成时：

```text

Pause
Server restart
```

所以：

```text

```

不能丢掉结果。

增加 Reflection Run：

```text

```

```text

```

把最近尚未 delivered 的 Reflection 加入：

```text
RESUME CONTEXT

Pending reflection review:
...
```

然后：

```text
deliveredAt = now
```

# Part II — Manager Agent

# 28. Manager 正式定位

Manager 不负责：

```text
解题
读附件
分析 PCAP
看图片
运行 Crypto
```

Manager 负责：

> **在几十道题中决定“现在让哪些题占用有限 Solver Slot”。**

---

# 29. Manager 是 Stateless

强烈建议：

```text
每一次 Replan
=
独立一次 Manager 调用
```

Manager 状态来源：

```text
SQLite
```

而不是：

```text
长期 Manager Conversation
```

流程：

```text
DB
↓
ManagerSnapshotBuilder
↓
Manager LLM
↓
DispatchPlan
↓
Policy Engine
↓
Scheduler
```

这使 Crash Recovery 极其简单。

# 36. Candidate Pre-filter

先由 deterministic scheduler 做便宜预筛选。

一定包含：

```text

```


```text

```


非常重要：

Manager 的：

```text

```


# 42. HOLD 的真实含义

```text

```

不是：

```text

```

只是：

```text

```

Challenge 仍然：

```text
QUEUED
```

```text

```

# 43. CONTINUE

用于 ACTIVE Challenge。

表示：

```text
Manager 建议保留当前 Solver
```

目前只是观测/审计信息。

不需要任何状态转换。

# 44. 未出现在 Plan 里的题

定义明确默认语义：

对于：

```text
QUEUED Candidate
```

如果没出现在 Manager Plan：

```text
默认 HOLD
```

对于：

```text
ACTIVE
```

没出现：

```text
默认 CONTINUE
```

这样 Manager 不必给 40 道题逐条输出 HOLD。

```text

You DO NOT solve challenges.

Your only task is to decide which supported challenges should consume the limited solver slots now.

The system supports only Misc and Crypto.

A challenge can have at most ONE solver.

Prioritize:
- likely easy challenges;
- challenges with high solve counts when that suggests lower difficulty;
- challenges with strong current progress;
- useful point value;
- cheap/light challenges when information is limited;
- keeping solver slots productively occupied.

Avoid:
- assigning unsupported challenges;
- assigning already solved challenges;
- spending every slot on speculative hard challenges;
- changing manually locked decisions.

Reflection is a short independent review, not another solver.
You may recommend whether reflection should be enabled.

Do not provide hidden reasoning.
Return only the required structured dispatch plan.
```

# 结论

MVP-2.5 可以浓缩为三个层次：

```text
第一层
Manager 决定
“哪几道题现在值得占 Solver Slot”

第二层
Solver 负责
“这道题具体怎么解”

第三层
Reflector 负责
“这个 Solver 当前是不是走偏了”
```

权限关系固定为：

```text
Manager
    ↓ proposal
Policy
    ↓
Scheduler
    ↓
Solver

Solver
    ↑ advice
Reflector
```

而不是：

```text
Manager → 直接控制 Worker

Reflector → 第二个 Solver
```

这个版本做完以后，RioMisc 就会从 MVP-2 的“**很多题都能单独自动解**”，真正进入“**一次给我几十道题，我自己决定先做谁，并且每个 Solver 卡住时能够获得独立复盘**”的阶段。

至于 Challenger、多 Solver、经验复用、Skill 学习、基于历史表现的 EV 调度，都可以很干净地留给 MVP-3，不会污染这版的开发目标。
