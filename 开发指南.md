# 西湖论剑 RioMisc — CTF Misc/Crypto Autonomous Agent Runtime

## MVP-1 极致详细开发指南

**文档版本：** MVP-1 / Architecture Draft 1.0
**目标读者：** 编程 Agent、开发人员、项目维护者
**开发目标：** 从零实现一个能够真实接入 CTF 比赛、自动发现/下载题目、调度 Pi Solver、并行解题、获取 Hint、验证 Flag、限速自动提交、持久化恢复，并支持 Web Dashboard + CLI 人工干预的完整 MVP。

---

# 0. 先读这一节：MVP-1 到底要做成什么

MVP-1 的目标**不是**：

> 做一个能解决所有 Misc/Crypto 题目的超级 Agent。

MVP-1 的目标是：

> 先做出一个稳定、可恢复、可观察、可并行运行的 CTF Autonomous Runtime，然后在这个 Runtime 中放入第一版 Misc/Crypto Solver。

最终必须能够完整跑通：

```text
比赛 API
   ↓
发现新题
   ↓
同步题目信息
   ↓
识别是否 Misc/Crypto
   ↓
自动 Start Challenge
   ↓
自动下载附件
   ↓
自动建立独立 Workspace
   ↓
Triage
   ↓
进入 Scheduler
   ↓
并行分配 Solver
   ↓
Pi Agent 开始解题
   ↓
调用 Python / Linux / Crypto / Misc 工具
   ↓
周期性记录进度
   ↓
10 分钟 Hint Eligible
   ↓
根据策略决定是否取 Hint
   ↓
继续解题
   ↓
发现 Candidate Flag
   ↓
Verifier
   ↓
Submission Manager
   ↓
赛事 API
   ↓
Correct → SOLVED
Wrong   → 反馈 Solver 继续分析
```

同时必须支持：

```text
程序崩溃
↓
重新启动
↓
读取数据库
↓
恢复 Challenge
↓
恢复 Pi Session
↓
恢复 Workspace
↓
继续比赛
```

还必须支持：

```text
ctf solve ./challenge
```

这种**完全不依赖比赛 API 的单题模式**。

# 4. 关于 Pi 的实现原则

当前 Pi SDK 提供程序化 `createAgentSession()`、AgentSession 生命周期、事件订阅、模型切换、自定义工具和 Session persistence 等能力，因此 MVP-1 适合直接把 Pi 作为 Solver Agent Harness 使用。

Pi Agent Core 还提供 AgentMessage、上下文转换、Tool Execution 生命周期等较底层能力。

Pi 当前自定义 Provider 能覆盖 OpenAI-style Completions、OpenAI Responses 和 Anthropic Messages，这与本项目需要的三种 Provider Protocol 基本一致。

但是 Pi 本身不负责 filesystem/process/network 权限隔离，因此不要把 Pi 的 `bash` 当成 Sandbox。隔离必须由本项目自己的 Tool Runtime / Docker 层完成。

**最关键原则：**

业务代码不得到处直接调用：

```ts
createAgentSession(...)
```

必须建立：

```text
AgentRuntimeAdapter
```

即：

```ts
interface AgentRuntime {
    createSession(...): Promise<AgentSessionHandle>
    resumeSession(...): Promise<AgentSessionHandle>
    sendMessage(...): Promise<void>
    switchModel(...): Promise<void>
    abort(...): Promise<void>
}
```

唯一直接依赖 Pi 的位置：

```text
src/agent/pi/
```

这样未来升级 Pi 或更换 Agent Harness 时不会污染整个系统。

# 23. Event Dispatcher

MVP-1 不需要 Kafka。

使用：

```text
SQLite domain_events
+
in-process dispatcher
```

状态修改和 event insertion 在同一个 transaction。

Dispatcher：

```text
SELECT *
FROM domain_events
WHERE processed_at IS NULL
ORDER BY created_at
LIMIT 100
```

处理成功：

```text
processed_at = now
```

这样即使：

```text
DB commit
↓
程序立刻 crash
```

# 134. 给编程 Agent 的最终执行要求

如果这份文档交给 Coding Agent，实现时必须遵循以下原则：

1. 不擅自扩大 MVP 范围。
2. 每个模块先定义接口和测试，再写实现。
3. 所有外部依赖都必须隔离在 Adapter 层。
4. 所有 Challenge 状态变化都必须经过 State Machine。
5. 所有 Contest 写操作必须经过 Control Plane。
6. Solver 永远不能直接 Submit Flag。
7. Solver 永远不能读取其他 Challenge。
8. 所有附件必须流式处理。
9. 所有 Tool Output 必须限制大小。
10. 所有 Worker 必须可恢复。
11. 所有 Pi Session 必须持久化。
12. 所有 API Key 必须隔离。
13. 每个重要行为必须产生可查询 Event。
14. 每个错误必须明确区分 recoverable / fatal。
15. 每个 Phase 完成后必须运行测试。
16. 不允许为了“看起来高级”提前加入 Redis/Kubernetes/RAG。
17. MVP-1 的首要指标是稳定性和完整闭环，其次才是解题覆盖率。

# 135. 一句话架构原则

整个 MVP-1 可以用三句话概括：

> **Control Plane 决定比赛怎么打。**

> **Pi Solver 决定一道题怎么解。**

> **Tool Runtime 决定 Agent 可以安全地做什么。**

如果这三层始终保持解耦，那么比赛当天即使 API 形式、Hint 规则、模型供应商或者题目数量发生变化，也只需要修改局部模块，而不会迫使整个系统重写。

# 136. MVP-1 开发优先级最终排序

严格按照：

```text
State Machine
      ↓
Persistence
      ↓
Mock Contest
      ↓
Scheduler
      ↓
Worker Recovery
      ↓
Pi Runtime
      ↓
Tool Runtime
      ↓
Submission
      ↓
Basic Solver
      ↓
Dashboard
```

而不是：

```text
先写一个很聪明的 Solver
↓
再想怎么接比赛
```

前一种方案才能最终形成真正能够参加比赛的 Autonomous CTF Runtime。

**MVP-1 的成功标准不是“Agent 偶尔能解出一道题”，而是“整个系统可以无人值守地稳定跑完整场比赛，并且任何一个 Solver、模型调用或主进程出现故障后都不会丢失整个比赛状态”。**
