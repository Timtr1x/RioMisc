是，检查后可以明确确认：**这个问题真实存在，而且应该进入 MVP-2.5 的正式范围。**

当前实现有两个直接问题。

第一，`TOOL_IMPLS` 目前正好有 **50 个工具**，而 `PiAgentRuntimeAdapter.#buildTools()` 对整个 `TOOL_IMPLS` 直接 `map()` 成 `customTools`，因此 Solver 创建 Session 时一次性拿到全部 50 个工具，没有 Misc/Crypto、文件类型、当前求解阶段等过滤。

第二，问题不只是工具太多。当前 Pi 的 `toolParameterSchema()` 只有大约 20 个 Tool 有单独参数定义，其余工具最终走：

```ts
default:
    return Type.Object({});
```

这意味着大量后来增加的 Misc Semantic Tools 和**几乎整批 Crypto Tools**，模型看到的参数 schema 是空对象。与此同时，运行时的 `cryptoTextSchema` 实际支持 `n/e/c/p/q/e1/e2/c1/c2/n1/n2/n3/m/m2/matrix/g/h/...` 一大堆字段。

例如：

```text
rsa_common_modulus
description:
"Common-modulus RSA (n,e1,c1,e2,c2)."

Pi schema:
{}

真实 runtime 期待:
n
e1
c1
e2
c2
```

再比如 `crt`、`xor_bytes`、`lll_reduce`，实际输入语义都有细节，但目前 Tool description 只有一句话。Crypto Prompt 主要告诉模型 RSA 的攻击顺序，并没有教授每个工具的精确输入、输出和失败语义。

所以我建议把这个提升为 **MVP-2.5 第三个核心能力**：

> **Progressive Tool Disclosure + Tool Curriculum**
>
> 即：工具不要一股脑全部告诉模型；模型需要什么工具时再发现、学习其完整用法、然后调用。

下面这部分应正式并入上一版 MVP-2.5 开发指南。

# MVP-2.5 新增核心模块

# Progressive Tool Disclosure & Tool Curriculum

MVP-2.5 最终三个核心能力改为：

```text
MVP-2.5

① Manager Agent
   几十题里决定先解谁

② LLM Reflector
   单 Solver 卡住时独立复盘
```

第三项应视为 **MVP-2.5 DoD**，不是可选优化。

# 26. 当前 Crypto Tools 的最低完整教学要求

下面这些必须全部有 Tool Manual。

| Tool                      | 必须教清楚的输入                                 |
| ------------------------- | ---------------------------------------- |
| `parse_crypto_values`     | `text` 或 `path`，只负责解析，不攻击                |
| `analyze_rsa_instance`    | `n,e,c` 或解析来源；只分析候选攻击                    |
| `rsa_small_e`             | `c,e,n?`                                 |
| `rsa_fermat`              | `n`                                      |
| `rsa_wiener`              | `n,e`                                    |
| `rsa_common_modulus`      | `n,e1,c1,e2,c2`                          |
| `rsa_hastad`              | `e,n1,c1,n2,c2,n3,c3`                    |
| `rsa_basic_decrypt`       | `n,c,e?,p?,q?`                           |
| `factor_integer`          | `n`                                      |
| `integer_root`            | `c,e`                                    |
| `mod_inverse`             | `a,m`                                    |
| `gcd`                     | `a,b`                                    |
| `extended_gcd`            | `a,b`                                    |
| `crt`                     | `a,m,b,m2`，当前是两组 congruence              |
| `solve_linear_congruence` | `a,b,m`，求 `ax ≡ b mod m`                 |
| `lcg_recover`             | `samples`                                |
| `aes_inspect`             | `path` 或 HEX ciphertext                  |
| `frequency_analysis`      | 文本                                       |
| `xor_bytes`               | 当前 `a=hex data`，`b/key=UTF-8 key`        |
| `xor_known_plaintext`     | `c=hex ciphertext`,`p/m=UTF-8 plaintext` |
| `lll_reduce`              | `matrix`，JSON matrix 或 whitespace rows   |
| `discrete_log_if_small`   | `g,h,m`                                  |

特别是 `xor_bytes` 当前实现里 `a` 作为 hex，而 `b/key` 按 UTF-8 读取，这种细节仅凭现在一句 `"XOR two byte strings (hex + key)."` 是不足以让模型稳定正确调用的。

# 58. 我会把这个提高到 MVP-2.5 的高优先级

目前的三个最重要工作我会重新排序：

```text
P0
Progressive Tool Disclosure
+ 完整 Tool Contracts

P0
真正 LLM Reflection

P0
Manager Dispatch
```

其中 Tool Disclosure 甚至应该排在 Reflection 前。

原因很简单：

现在 Solver 已经有不少真正可用的 Misc/Crypto 能力，**问题开始从“没有工具”变成“工具太多、模型不知道哪一个、甚至不知道怎么传参数”。**

这恰好说明系统进入了下一个阶段。

MVP-1 时：

```text
工具不够
```

MVP-2 时：

```text
工具快速增加
```

MVP-2.5 必须开始解决：

```text
Tool Scaling
```

最终应该让 Solver 的体验变成：

```text
我需要检查 RSA
        ↓
discover_tools("RSA analyze")
        ↓
analyze_rsa_instance

结果：
small-e unlikely
Fermat plausible
Wiener plausible

        ↓
get_tool_help("rsa_fermat")
        ↓
知道：
输入 n
适合 p≈q
输出 p,q

        ↓
execute_tool(...)
        ↓
得到证据
```

而不是现在这种：

```text
启动
↓
50 个工具突然全部出现
↓
rsa_fermat
crt
lll_reduce
spectrogram
pcap
bitplane
...
↓
其中大约 30 个在 Pi schema 里甚至表现成 {}
```

所以这个点我认为不是“小优化”，而是 **MVP-2.5 必须补的 Solver Tool Architecture**。完成后再往后增加 Sage、更多 Crypto attacks、更多取证工具时，也不会出现“每新增一个工具，模型上下文里再多塞一个 function schema”的线性恶化。
